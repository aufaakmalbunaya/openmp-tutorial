1 The OpenMP execution model
OpenMP is an application programming interface for parallel programming in C, C++, and Fortran.
Its CPU programming model lets threads in one process access shared memory. Its interface includes
compiler directives, runtime functions, and environment variables [1].

1.1 Process, thread, and core
• A process is a running program with its own address space.
• A thread is an execution stream inside a process. Threads have their own execution state while
accessing the process’s shared data.
• A CPU core is a hardware execution resource. A logical CPU may represent a hardware thread
rather than a separate physical core.
Requesting four OpenMP threads does not create four physical cores. The operating system schedules
software threads onto the CPU resources available to the process. In a VM, virtual CPUs also
depend on host scheduling.

1.2 Parallel regions and worksharing
An ordinary program begins with one thread. When that thread encounters #pragma omp parallel,
a team executes the region. The encountering thread participates as thread 0. At the region’s end,
the team synchronizes and the encountering thread continues after the region [2]. This is commonly
described as a fork–join model; an implementation may reuse worker threads across regions.

1

/* Executed by the initial thread. */
#pragma omp parallel
{
/* Every thread in the team executes this block. */
}
/* The initial thread continues here. */

Creating a team does not divide a loop automatically
parallel starts a parallel region. for distributes loop iterations among an existing team.
parallel for combines those two actions. An ordinary loop inside a parallel region is
executed in full by every thread unless you add an appropriate worksharing construct.

6 Exercise 4: Fix accumulation with a reduction
Goal: understand a data race and select an appropriate synchronization mechanism.

Why the obvious parallel sum is wrong
Suppose n is already defined. This fragment is intentionally incorrect:
Listing 6: Incorrect fragment: unsynchronized shared updates
1
2
3
4
5

long long sum = 0;
#pragma omp parallel for shared(sum)
for (long long i = 1; i <= n; ++i) {
sum += i; /* Data race: multiple threads update sum. */
}

sum += i involves reading and updating shared state. Two threads can read the same old value and
overwrite one another’s updates. More generally, this is a data race, so the program’s behavior is not
defined by the model. It may even print the expected answer on some runs. A successful-looking
run does not prove correctness, and volatile does not repair the race.

Three correct versions
A reduction gives participants private accumulators and combines them at the end. An atomic
update protects a supported update of one storage location. A critical region allows one thread at a
time to execute a block. For this simple sum, reduction avoids synchronizing every addition [5].

#include <stdio.h>

int main(void)
{
const long long n = 1000000;
const long long expected = n * (n + 1) / 2;
long long sum_reduction = 0;
long long sum_atomic = 0;
long long sum_critical = 0;
#pragma omp parallel for default(none) shared(n) \
reduction(+:sum_reduction) schedule(static)
for (long long i = 1; i <= n; ++i) {
sum_reduction += i;
}
#pragma omp parallel for default(none) \
shared(n, sum_atomic) schedule(static)
for (long long i = 1; i <= n; ++i) {
#pragma omp atomic update
sum_atomic += i;
}
#pragma omp parallel for default(none) \
shared(n, sum_critical) schedule(static)
for (long long i = 1; i <= n; ++i) {
#pragma omp critical(sum_guard)
{
sum_critical += i;
}
}
printf("Expected : %lld\n", expected);
printf("Reduction: %lld\n", sum_reduction);
printf("Atomic

printf("Critical : %lld\n", sum_critical);

sum_atomic == expected &&
sum_critical == expected);

The synchronization rules you used
• omp for has an implicit barrier at its end unless nowait removes it.
• single selects one thread in the team to execute the block; it need not be thread 0. It normally
has an implicit barrier at its end. It does not provide an entry barrier.
• barrier explicitly makes the team wait until all members reach that point; the synchronization
also establishes the required visibility of preceding shared-memory operations.
• The end of the parallel region synchronizes the team before the code after the region continues.

Why each directive matters
• single ensures one thread generates the task set once.
• firstprivate(i) captures the iteration’s index when the task is generated. Each task keeps the
index it needs even if it runs later.
• The shared arrays remain alive until all the tasks complete; each task writes its own element.
• Plain taskwait waits for previously generated child tasks of the current task. Here that makes
every result ready before printing. It is not a general team barrier or an automatic wait for all
descendants of arbitrary tasks [7].

Your tasks
1. Run with 1, 2, and 4 threads. Can one thread execute multiple tasks?
2. Explain why task count and thread count are different quantities.

of single would occur too late.
4. Extend each task to perform a different amount of numerical work and keep a serial version for
validation. Do not use sleep time as a substitute for computational work when studying CPU
speedup.
Granularity matters
The square calculations above are intentionally tiny and demonstrate semantics. Creating tasks
for such small work usually costs more than doing the arithmetic. Use larger jobs or combine
small jobs before expecting a speedup.

Validate before interpreting speed
For the supplied large n, both estimates should be close to 3.141592653589793. The program reports
two different checks:
• difference: agreement between serial and parallel implementations.
• reference_error: accuracy relative to the library’s value of π, including both integration and
floating-point error.
The exit status checks serial–parallel agreement against 10−8 , a practical tolerance for this exercise’s
recommended sizes. If you change the algorithm or greatly change the input size, reconsider the
tolerance. Matching implementations can share the same error, so also inspect the reference error.

Understand the timer
omp_get_wtime() returns elapsed wall-clock time in seconds. Both reads for a duration are made by
the same thread [8]. The timed parallel interval includes team entry, loop execution, synchronization,
and reduction. It excludes the warm-up and printed output. It is a kernel benchmark, not an
end-to-end application benchmark.

Your measurement procedure
1. Record CPU model, logical CPU count, VM vCPU count if applicable, compiler version, flags,

2. Use the same executable and input size for every thread-count comparison. Check the actual

12.1 A practical review checklist
1. Ownership: for each shared object, identify who reads and writes it. Distinct array elements
can be independently writable; a shared scalar accumulation normally requires coordination.
2. Initialization: initialize private variables before use. Use firstprivate only when an initial
value is actually needed.
3. Dependencies: prove required producer work completes before consumers access its result. Use
nowait only with that proof.
4. Validation: compare all relevant outputs with a serial result or an independent reference, not
just a few printed elements.
5. Measurement: keep input, flags, and timed work consistent. Save raw runs and report actual
team sizes.
